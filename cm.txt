fix(harness): the migration-gate skill was unroutable, and --emit-docs does not write the graph

harness_eval was failing one check: "skill:architecture-migration-gate — skill has
no triggers, agent can't route to it". Two stacked causes, and the second is a
footgun worth writing down.

1. The skill declared `trigger:` — singular, one prose sentence. The graph indexes
   `triggers` (plural, keyword list); `trigger` is not read at all. So the gate
   built to catch documentation drift could not itself be discovered by any agent,
   which is the same failure one level up.

   Kept on ONE line deliberately. _read_frontmatter is line-based — splitlines()
   plus partition(":"), not a YAML parser — so a wrapped list silently loses every
   line after the first. My first fix wrapped it and still read as zero triggers.

2. `build_capability_graph.py --emit-docs` regenerates the routing DOCS
   (WHEN_TO_USE_*, INDEX) but does NOT write CAPABILITY_GRAPH.json. The plain
   command does. The handoff ran only --emit-docs, so the graph on disk stayed
   stale and every later verification read the old node.

   That is why the first fix appeared not to work: the frontmatter parser was
   reading 14 triggers correctly the whole time while the graph file still said
   zero. I confirmed by calling _read_frontmatter directly rather than trusting
   the graph.

   I also hid the rebuild's output behind >/dev/null while assuming it had
   worked, which is the same mistake in miniature.

After: routing 2/2, harness_eval clean on every slice. `capability_query resolve
"we are migrating off supabase, run the doc sweep"` now ranks the gate second.

Proof: graph node carries 14 triggers; harness_eval shows boundary 2/2, guards
1/1, live-health 4/4, lockstep 1/1, model-call 1/1, routing 2/2.
