# Bravo Session Handoff — 2026-05-13

## TL;DR

CC opened this session having been blocked by a broken onboarding flow: every fresh signup landed on a legacy `/onboarding` page that single-selected from the OASIS C-suite (Bravo/Atlas/Maven/Aura/Hermes/Lumen) and forced a paid API-key paste, with no path to the SunBiz agents. CC asked to "fix and build for them" — comprehensively, not patches.

Over this session we:

1. Killed the legacy `/onboarding` page; replaced it with a 5-step industry-template wizard at `/onboarding/wizard` that includes a real multi-select agent picker.
2. Expanded the SunBiz manifest from a single Solara agent to a **two-agent package** (Solara operational + Helios sales-facing) and renamed the Suga tenant's "Suga Sean" persona to a 4-agent **Lyra package**.
3. Added tier metadata to the schema so wizard cards show pricing/setup signals.
4. Created CC's actual SunBiz test account in Supabase (`Submissions@sunbizfunding.com`) with the email pre-confirmed, the tenant brand-matched to the `sun` profile, and `onboarding_completed_at` set so signin lands at the dashboard.
5. Fixed the `/t/sun/settings` 404 by repointing the manifest nav at the existing tenant-aware `/settings` page.
6. Aligned brand subtitle to "Agent Command Center" across OASIS, SunBiz, Suga, and the funding template.
7. Added a `create_record` dashboard-action so Solara/Helios can write rows into the manifest data model via natural-language chat — "we just got a new funded deal, $50k ABC Corp" → row in `/t/sun/funded-deals`.

Production target: `https://agent-dashboard-cc90210.vercel.app`. All seven changes are deployed.

- **SunBiz Funding Pack** — Solara (operational), Helios (sales)

### AI-driven record creation

**File:** [lib/agent-actions.ts](../apps/command-center/lib/agent-actions.ts) — new `create_record` action.

Persona spec ([lib/agent-personas.ts](../apps/command-center/lib/agent-personas.ts)) teaches agents the marker:

```
<dashboard-action type="create_record">
{"entity":"funded_deal","data":{"lead_id":"...","amount_funded":50000,...}}
</dashboard-action>
```

Handler validates:
- entity exists in the tenant's manifest data_model
- required fields present
- enum values match
- date/datetime fields parse as YYYY-MM-DD / ISO-8601
- number fields are finite

Then calls the same `createRecord` API used by the manual "New <entity>" form. Tenant-scoped via `ctx.tenantId`, audit-logged via `logAction`. The next page load shows the row in the matching tab.

## Architecture decisions made this session

### Why two onboarding paths collapsed into one

Originally there were two: `/onboarding` (legacy bridge-pair + API-key + persona-pick for the OASIS operator) and `/onboarding/wizard` (new industry-template flow for client tenants). The first was hardcoded to the OASIS C-suite and forced an API-key paste; client tenants who hit it had no way to pick SunBiz or Lyra agents.

CC's instruction was unambiguous: *"You need to fix this immediately and ensure it is 100% closed loop."* Two paths is the wrong shape. The wizard's industry-template structure cleanly handles every persona: pick "Custom (C-Suite)" → C-suite package shown; pick "Business Funding" → Solara/Helios pre-checked. Bridge pairing + API keys live in Settings, where they belong. The legacy `/onboarding` URL is now a redirect for backward compatibility.

### Why brand-string matching stays despite manifest system

The Phase 1 manifest system (`tenant_manifests` table) is the long-term architecture. But it doesn't cover the seed slugs (sun/suga/oasis) — those live in `lib/manifest/seeds.ts` as code-defined defaults. For a client like SunBiz who signed up before any wizard run, the brand string "Sun Biz Funding" → `command_center_profile_slug = "sun"` in `tenants.custom_fields` is the link that makes `resolveDataTenant` grant data access. This dual path (manifest row OR brand-match fallback) is documented in `lib/manifest/tenant-scope.ts` and is the current source of truth.

### Why `create_record` doesn't take the manifest slug from the agent

The handler reads it from the tenant's `custom_fields.command_center_profile_slug`. Letting the agent pass the slug as part of the payload would let a misconfigured agent prompt write into the wrong tenant's records. The tenant_id from ctx is the authoritative scope; the slug is just for entity-schema lookup.
