📱 Part 1: notify.py — Your Real-Time Alert System

Telegram replaces Slack for internal notifications. It is free, instant, and works on every device. notify.py is a single-function wrapper that every other engine imports to fire alerts.

BotFather Setup (10 minutes)

1. Open Telegram and search for @BotFather

2. Send /newbot — follow the prompts, give your bot a name

3. BotFather gives you a bot token — looks like 7845123456:AAF-something-long

4. Start a chat with your new bot (search for it by name)

5. Send it any message, then visit: https://api.telegram.org/bot<YOUR_TOKEN>/getUpdates

6. Find "chat":{"id":... in the response — that is your Chat ID

Add both to .env.agents:

TELEGRAM_BOT_TOKEN=7845123456:AAF-your-bot-token

TELEGRAM_CHAT_ID=123456789

Category-Based Notifications

Every engine sends notifications with a category prefix so you know at a glance what fired:

• lead — New lead added, stage change, lead qualified

• email — Email sent, sequence enrolled, open/click tracked

• booking — Slot booked, booking cancelled, reminder sent

• content — Post published, post failed, calendar reminder

• revenue — New payment, subscription change, MRR milestone

• instagram — DM received, comment flagged, auto-reply sent

• system — Scheduler job ran, error caught, health check result

Usage from any engine:

from notify import notify

notify("lead", f"🎯 New lead qualified: {lead['name']} from {lead['company']}")

⚡ QUICK WIN: Test your bot right now. Run:

python scripts/notify.py test

You should get a message in Telegram within 2 seconds. If you don't, check your token and chat ID. Get this working before you touch any other engine in this lesson.

📸 Part 2: instagram_engine.py — DM Automation Without the ManyChat Tax

ManyChat charges $15–$99/month to automate Instagram DMs. instagram_engine.py uses a persistent Playwright browser session stored in tmp/ig-browser/ and handles DM checking, auto-replies, and comment monitoring through the Instagram web interface directly.

This is the same approach used in the production system. It has been tested: sent a real auto-reply in CC's voice, confirmed via Telegram notification.

How the Persistent Session Works

The first time you run the engine, it launches a browser, navigates to instagram.com, and waits for you to log in manually. After login, it saves the browser session state to tmp/ig-browser/. Every subsequent run restores that session — no login required, no 2FA prompts, no captcha.

Add credentials to .env.agents:

INSTAGRAM_USERNAME=your_username

INSTAGRAM_PASSWORD=your_password

Commands

check-dms — Scan unread DMs and log them to Supabase

python scripts/instagram_engine.py check-dms

send-dm — Send a DM to a specific user

python scripts/instagram_engine.py send-dm --username "prospect_handle" --message "Hey, saw your post about..."

check-comments — Scan recent post comments and flag replies needed

python scripts/instagram_engine.py check-comments --post-id "abc123"

log-dm — Manually log a DM interaction to the lead engine

python scripts/instagram_engine.py log-dm --username "prospect_handle" --direction inbound --content "They asked about pricing"

Auto-Reply Logic

The scheduler runs check-dms every 15 minutes. When a new DM matches a trigger keyword (configurable in Supabase ig_auto_replies table), the engine fires send-dm with the corresponding reply template and logs the interaction to the lead engine.

Example trigger config in Supabase:

keyword: "pricing"

reply: "Hey! Thanks for reaching out. Our packages start at $1,500/month — I'll send you a full breakdown. What's your email?"

⚠️ WARNING: Instagram's automation policies prohibit bulk unsolicited DMs. Use this for reply automation — responding to people who message you first — not for cold outreach blasts. The persistent session approach is also more fragile than an official API; if Instagram changes their web interface, the selectors may break. Check the engine monthly.

💀 COMMON MISTAKE: Running check-dms too frequently. Every 15 minutes is the right cadence. Every 1 minute triggers rate limiting and risks account flags. The scheduler handles the timing — don't run it manually on a loop.

⚙️ Part 3: scheduler.py — The 24/7 Conductor

Everything you have built so far runs on demand. The scheduler makes it all autonomous. It reads cron jobs from Supabase, executes them on schedule, and fires Telegram notifications on completion or failure.

Cron Jobs Table Schema

id — bigint, primary key

name — text (human-readable job name)

command — text (full shell command to run)

schedule — text (cron expression: "*/15 * * * *")

enabled — boolean, default true

last_run — timestamptz

last_status — text (success/error)

error_message — text

created_at — timestamptz, default now()

The 12 Pre-Seeded Cron Jobs

These are the jobs running in the production stack:

check-instagram-dms — Every 15 minutes: python scripts/instagram_engine.py check-dms

morning-followups — 8AM daily: python scripts/lead_engine.py followups --json | python scripts/notify.py pipe lead

email-sequence-processor — Every hour: python scripts/email_engine.py sequence process-due

booking-reminders-24h — 9AM daily: python scripts/booking_engine.py remind --hours 24

booking-reminders-1h — Every hour: python scripts/booking_engine.py remind --hours 1

content-publisher — Every hour: python scripts/content_engine.py due --hours 1 --json | python scripts/scheduler.py dispatch-content

revenue-daily-sync — 6AM daily: python scripts/revenue_engine.py sync --source stripe

revenue-weekly-report — 7AM Monday: python scripts/revenue_engine.py report --period week | python scripts/notify.py pipe revenue

lead-score-refresh — 2AM daily: python scripts/lead_engine.py score --all

health-check — Every 30 minutes: python scripts/scheduler.py health --json | python scripts/notify.py pipe system

session-log-compress — 3AM Sunday: python scripts/memory_tool.py compress-logs

stripe-webhook-verify — Every 6 hours: python scripts/revenue_engine.py verify-webhooks

💡 PRO TIP: Store cron jobs in Supabase, not in a crontab file or hardcoded config. This means you can enable, disable, or modify jobs from anywhere — your phone, Claude Code, a script — without SSHing into a server. The scheduler reads the table on each tick. Change the table, change the schedule.

PM2 Deployment

PM2 keeps the scheduler running 24/7 and restarts it automatically after crashes or reboots.

Install PM2:

npm install -g pm2

Start the scheduler:

pm2 start "python scripts/scheduler.py run" --name "bravo-scheduler" --interpreter none

Enable auto-start on system reboot:

pm2 startup

pm2 save

Monitor running jobs:

pm2 logs bravo-scheduler

pm2 status

Stop the scheduler:

pm2 stop bravo-scheduler

⚠️ WARNING: The scheduler reads .env.agents for credentials. If you rotate any API key, update .env.agents and run pm2 restart bravo-scheduler. The process reads the file at startup, not at each job execution.

💰 Part 4: revenue_engine.py — MRR Dashboard

Baremetrics charges $99/month to show you your Stripe data in a dashboard. revenue_engine.py talks directly to the Stripe API and gives you the same metrics in your terminal — and in Telegram on Monday mornings.

Commands

sync — Pull latest data from Stripe into Supabase

python scripts/revenue_engine.py sync --source stripe

dashboard — Show current MRR, ARR, active subscribers, churn rate

python scripts/revenue_engine.py dashboard

forecast — Project MRR for next 90 days based on current trend

python scripts/revenue_engine.py forecast --days 90

goal — Set and track an MRR goal

python scripts/revenue_engine.py goal --target 5000 --currency usd --deadline "2026-05-15"

report — Weekly or monthly revenue summary

python scripts/revenue_engine.py report --period week

Connecting to Stripe

Add to .env.agents:

STRIPE_SECRET_KEY=sk_live_your_key_here

The engine uses the Stripe Python SDK, not the MCP (which is broken in v0.3.1). The sync command pulls customers, subscriptions, and payments into Supabase so you have a local copy of your revenue data that does not depend on Stripe being up.

🗺️ The Full Stack: How All 11 Engines Connect

Here is the complete picture of how the system works together:

Data layer: Supabase — every engine reads and writes here. One source of truth.

Notification layer: notify.py — every engine imports this. All alerts go to Telegram.

Orchestration layer: scheduler.py — reads cron_jobs from Supabase, calls each engine on schedule.

Engine layer (all 11 tools):

• lead_engine.py — contacts, interactions, scoring, pipeline

• email_engine.py — sends, templates, sequences

• booking_engine.py — slots, bookings, confirmations, reminders

• content_engine.py — calendar, scheduling, Late MCP dispatch

• instagram_engine.py — DM monitoring, auto-replies

• revenue_engine.py — Stripe sync, MRR tracking, forecasting

• notify.py — Telegram alerts (imported by all engines)

• supabase_tool.py — raw database access for debugging

• stripe_tool.py — raw Stripe access for debugging

• edit_content.py — FFmpeg video pipeline

• memory_tool.py — session log compression, archive management

A typical autonomous day looks like this:

6AM — revenue_engine.py sync pulls overnight Stripe activity

7AM (Monday) — weekly revenue report fires to Telegram

8AM — lead_engine.py followups sends your priority call list to Telegram

Every 15min — instagram_engine.py check-dms scans for new messages, auto-replies to trigger keywords

Every hour — due email sequences send, booking reminders fire, due content posts to Late MCP

Every 30min — health check confirms all jobs are running, alerts on any failures

Your phone — Telegram notifications for new leads, bookings, DM replies, payments

You: open Telegram, see what happened overnight, make three decisions, close Telegram. The rest ran itself.
