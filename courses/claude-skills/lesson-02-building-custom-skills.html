🛠️ Building Custom Skills — Your AI's Skill Tree

XP Reward: +125 XP | Running Total: 200 XP

Level: Builder (L1) — Creating tools that multiply your output.

Custom skills are reusable prompt templates that YOU create. They're markdown files that define specialized behaviors Claude Code can execute on command. Think of them as macros — except instead of recording keystrokes, you're recording expert-level workflows that fire every time.

⚡ QUICK WIN: Every skill you build saves 5-10 minutes per use. Build 10 skills, use each 3x/day = 2-3 hours saved daily. That's not optimization — that's a competitive advantage.

📁 Where Skills Live

Skills are markdown files stored in specific directories:

📂 Project-level: .claude/commands/your-skill.md — Available only in this project. Triggered with /project:your-skill.

🌍 Global-level: ~/.claude/commands/your-skill.md — Available in every project. Triggered with /user:your-skill.

Project skills override global ones with the same name. This lets you have a generic /commit globally and a specialized one per project.

🧬 Anatomy of a Skill

Every skill is a markdown file with optional YAML frontmatter:

---

description: Code review with security focus

---

Review the staged git changes for:

1. Security vulnerabilities (OWASP Top 10)

2. Hardcoded secrets or API keys

3. Missing error handling

4. TypeScript type safety issues

Then auto-fix any mechanical issues.

Ask before changing business logic.

That's it. Save as .claude/commands/review.md, trigger with /project:review. Instant expert code review every time.

💡 PRO TIP: The description field in frontmatter shows up when you type / and browse available commands. Write a clear one-liner so future-you knows what each skill does.

📝 Your First 5 Skills (Build These Now)

1. /commit — Smart Git Commits

---

description: Conventional commit with smart message

---

Look at staged changes (git diff --cached).

Write a conventional commit message (feat/fix/refactor/docs).

Keep the subject under 72 characters.

Include a 1-2 line body if the change isn't obvious.

Commit it.

2. /debug — Systematic Debugging

---

description: Root-cause debugging protocol

---

Read the error message carefully.

Search the codebase for the failing function.

Trace the data flow backward from the error.

Find the ROOT CAUSE — not the symptom.

Fix at the source. Verify the fix.

Never guess. Always trace.

3. /explain — Code Explainer

---

description: Explain code in plain English

---

Read the file or function I specify.

Explain what it does in plain English.

Include: purpose, inputs, outputs, side effects.

Flag anything that looks like a bug or risk.

4. /test — Write Tests First

---

description: TDD - write failing test first

---

For the feature or function I describe:

1. Write a failing test FIRST

2. Run it — verify it fails

3. Write minimal code to pass

4. Run again — verify it passes

5. Refactor if needed (keep tests green)

5. /ship — Deployment Checklist

---

description: Pre-deployment verification

---

Before deploying, verify:

1. npm run build passes with zero errors

2. No hardcoded secrets (grep for API keys)

3. No console.log in production code

4. Git status is clean

5. Push to remote and confirm

💀 COMMON MISTAKE: Making skills too complex. A 5-line skill that does one thing well beats a 50-line skill that tries to do everything. Keep each skill focused on a single workflow. You can always chain them: /review then /commit then /ship.

🔗 Dynamic Skills with Arguments

Skills can accept arguments using the $ARGUMENTS placeholder:

---

description: Refactor a function for clarity

---

Refactor the function: $ARGUMENTS

Goals: clearer naming, smaller functions, better types.

Keep the same external behavior. Run tests after.

Usage: /project:refactor handlePaymentWebhook — Claude knows exactly which function to refactor.

🧠 KEY TAKEAWAY: Skills are how you encode your expertise into reusable workflows. Every time you solve a problem the hard way, ask: "Can I turn this into a skill so I never solve it manually again?" The answer is almost always yes.
