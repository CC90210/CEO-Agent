🐛 Systematic Debugging

The #1 skill that separates amateurs from professionals. Random fix attempts waste time and create new bugs.

The Iron Law: No fixes without root cause investigation first.

The 4-Phase Protocol:

1️⃣ Investigate — Read the error message carefully. Reproduce consistently. Check recent changes. Trace the data flow backward from where it breaks.

2️⃣ Analyze — Find working examples of similar code. Compare. What's different between working and broken?

3️⃣ Hypothesize — "I think X is the root cause because Y." Test with the smallest possible change. One variable at a time.

4️⃣ Fix — Write a failing test that reproduces the bug. Fix the root cause. Verify the test passes.

💀 COMMON MISTAKE: "Just try changing X and see if it works." This is guessing, not debugging. If you haven't traced the data flow, you're guessing. Stop. Go back to Phase 1.

The 3-Strike Rule: If you've tried 3 different fixes and none worked, you're fixing the wrong thing. Step back and question the architecture — the problem is deeper than you think.

🔍 Code Review (Fix-First)

Every change gets reviewed before it ships. The Fix-First methodology: auto-fix everything mechanical, ask about everything that requires judgment.

Auto-fix without asking:

• Dead code (unused functions, imports)

• console.log left in production

• Hardcoded localhost URLs

• Unused variables and stale comments

• Missing TypeScript types

Always ask before touching:

• Security pattern choices (auth, encryption)

• Architecture changes (new abstractions, file restructuring)

• Business logic that seems wrong but might be intentional

• Error handling strategy (fail-silent vs fail-loud)

Severity levels:

🔴 CRITICAL — Data loss, secret exposure, auth bypass → Block. Fix immediately.

🟠 HIGH — Security hole, missing error handling on payments → Block.

🟡 MEDIUM — N+1 queries, type unsafety, missing loading states → Fix before merge.

🟢 LOW — Style, naming, dead comments → Auto-fix or note.

💡 PRO TIP: Build a /review skill that runs this checklist automatically. Run it before every commit. The 2 minutes it takes prevents the 2 hours debugging a production issue.

🧪 Test-Driven Development (TDD)

Write the test first. Watch it fail. Write minimal code to pass. This is not optional — it's how professionals build reliable software.

The TDD Cycle:

🔴 RED — Write a test that describes what SHOULD happen. Run it. Watch it fail.

🟢 GREEN — Write the simplest code that makes the test pass. Nothing more.

🔵 REFACTOR — Clean up while keeping tests green. Improve names, remove duplication.

Why test-first matters:

• Tests written after code pass immediately — that proves nothing

• Watching a test fail proves it actually tests the right thing

• Test-first forces you to think about edge cases before writing code

• You end up with a safety net that catches regressions forever

Example — Bug Fix:

// RED: Write the test

test('rejects empty email', () => {

const result = submitForm({ email: '' });

expect(result.error).toBe('Email required');

});

// Run → FAIL (no validation exists yet)

// GREEN: Minimal fix

if (!data.email?.trim()) return { error: 'Email required' };

// Run → PASS

💀 COMMON MISTAKE: "I'll write tests after to verify it works." Tests after = testing what you built, not what's required. You test what you remembered, not what you forgot. Test-first forces edge case discovery.

📝 Smart Commits

Conventional commit messages make your git history searchable and meaningful:

feat: add Stripe webhook handler for subscription events

fix: prevent empty cart from reaching checkout

refactor: extract email validation into shared util

docs: update API endpoint documentation

chore: upgrade Next.js from 14.1 to 14.2

Rules:

• Subject line under 72 characters

• Use imperative mood ("add feature" not "added feature")

• Body explains WHY, not WHAT (the diff shows what)

• Never commit .env files or secrets

• Commit often — small commits are easier to review and revert

🧠 KEY TAKEAWAY: These four skills — debugging, code review, TDD, and smart commits — are the foundation of professional software delivery. Master these and everything else builds on top. They're not fancy, they're not exciting, but they're the difference between shipping reliably and shipping chaos.
